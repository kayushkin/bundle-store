# About bundle-store

## What it owns

`:8307`. Registry of curated, inheritable **session bundles** — named sets of skills + tools, with optional model/effort defaults (which llm-bridge-server applies at session create since 2026-09-18, above the harness default and below the session's own value), selected for a session by repo tags plus task tags — plus the `/resolve` composition endpoint. Members are stored as skill-store and tool-store **ids**, with names carried alongside for display only. Since 2026-09-11 `POST /resolve` also takes `bundle_ids`: exactly those bundles (plus `base`, as always) expanded through their extends chains, for a session started with a chosen bundle rather than a tag match; an id that is missing or disabled is a **404** naming which, never a silently smaller bundle. This is what llm-bridge-server calls at spawn for a session's `bundle_id`. Since 2026-09-24 a member carries `effect`, `include` (the default, and what every older row became) or `deny` (tools only; a skill deny is a 400), served at `GET /member-effects`, and a bundle carries `denied_read_paths` (plain patterns starting `/` or `~/`, never a harness rule string). `/resolve` returns `denied_tools` and `denied_read_paths`, always present: a deny anywhere in the resolved set (selected bundles and their extends ancestors) wins over any include, so a denied tool is never in `tools`. That is how a bundle turns off a harness built-in such as tool-store's `claude_code.Write`. The effect's CHECKs in `schema.sql` repeat the Go list `MemberEffects`, and `TestTheSchemaChecksAgreeWithMemberEffects` keeps them in step. Wire types rendered to TypeScript by `./generate-ts.sh` as `@kayushkin/bundle-store-types` (since 2026-09-18, `store.go` and `settings.go` excluded). The four variables it reads, `BUNDLE_STORE_ADDR`, `BUNDLE_STORE_DATA_DIR`, `SKILL_STORE_URL` and `TOOL_STORE_URL`, are declared once in `settings.go` with llm-bridge `servicesettings` (hence `replace ../llm-bridge` in `go.mod`, which makes `deploy-gate` check that tree too) and served read-only at `GET /settings`. A new variable is declared there or `TestEveryEnvironmentVariableTheServiceReadsIsDeclared` fails, and a set `BUNDLE_STORE_` variable that nobody declared stops the service at boot; `deploy.sh` checks the running service's environment for one before it stops it, alongside the `-check-members` pre-flight. Declare nothing `Editable` while the service has no operator gate. `settings.go` defaults to `127.0.0.1:8307` and the unit says the same, because the service has no auth. Facts about this host's instance (its drop-in, the pinned skill id and why, who reads `BUNDLE_STORE_URL`) are in the noteboard note tagged `bundle-store`.

## Where this prompt lives

These sections are stored in agent-store as a project prompt collection and rendered, with identical text, to `AGENTS.md` and `CLAUDE.md` at the root of this repo, so that whichever file a harness reads it gets the same thing. Edit them on dash `/files`, or edit either rendered file: the 15-minute scan carries the edit back into the sections and out to the other file. The host prompt keeps one row for this repo with only what an agent elsewhere needs.

## Public repository: nothing personal

This repo is meant to be public. Nothing about the user or this host goes in it — not in code, tests, comments, commit messages or this prompt: no names of people, chats, accounts or machines, home directories, personal file paths or tokens. The unit file uses `%h`, never a home directory. Tests and the smoke script use made-up bundles and tags. A fact an agent here needs about this host goes in the noteboard note tagged `bundle-store`.
